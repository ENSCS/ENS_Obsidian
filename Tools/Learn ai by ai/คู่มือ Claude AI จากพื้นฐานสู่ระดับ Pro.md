## 1. Claude คืออะไร?

Claude คือ AI Assistant ที่พัฒนาโดย **Anthropic** บริษัท AI Safety จากสหรัฐอเมริกา ออกแบบมาให้เป็น AI ที่ฉลาด ซื่อสัตย์ และปลอดภัย

Claude ไม่ใช่แค่ chatbot ธรรมดา — มันคือผู้ช่วยที่อ่านเขียนได้ทุกภาษา วิเคราะห์เอกสารได้ เขียนโค้ดได้ และทำงานอัตโนมัติได้ด้วย

### Claude ทำอะไรได้บ้าง

```
✅ อ่านและเขียนข้อความทุกภาษา รวมถึงภาษาไทย
✅ วิเคราะห์และสรุปเอกสาร PDF, Word, Excel
✅ เขียนโค้ดและแก้ bug
✅ ตอบคำถามและให้คำแนะนำ
✅ สร้างเนื้อหาสร้างสรรค์ เช่น บทความ อีเมล รายงาน
✅ วิเคราะห์รูปภาพ
✅ ทำงานอัตโนมัติผ่าน API
```

### Claude เข้าถึงได้หลายช่องทาง

| ช่องทาง | เหมาะกับ | ราคา |
|---|---|---|
| claude.ai (เว็บ/แอป) | ใช้งานทั่วไป | Free / Pro $20/เดือน |
| Claude API | นักพัฒนา สร้าง Agent | จ่ายตาม Token |
| Claude Code | งานโค้ดบน terminal | ใช้ Pro account |
| Claude Desktop | ใช้ Tool และ MCP | ใช้ Pro account |

### เปรียบให้เห็นภาพ

```
Claude = พนักงานอัจฉริยะที่รู้ทุกเรื่อง
พร้อมทำงานตลอด 24 ชั่วโมง ไม่เคยเหนื่อย
แค่บอกว่าต้องการอะไร — ลงมือทำให้ทันที
```

## 2. Prompt คืออะไร?

**Prompt** คือคำสั่งหรือข้อความที่คุณส่งให้ Claude — มันคือหัวใจของทุกอย่างเลย

ยิ่งบอก Claude ละเอียดและชัดเจนเท่าไหร่ ผลลัพธ์ที่ได้ก็จะดีขึ้นเท่านั้น

> ถ้า Claude คือพนักงาน — Prompt คือคำสั่งงานที่คุณมอบให้

### ความแตกต่างของ Prompt ที่ดี vs ไม่ดี

**Prompt ไม่ดี:**
```
"สรุปนี้หน่อย"
```

**Prompt ที่ดี:**
```
"สรุปเอกสารนี้เป็นภาษาไทย ความยาวไม่เกิน 5 บรรทัด
เน้นประเด็นสำคัญที่ผู้บริหารควรรู้
ใช้ภาษาเป็นทางการ"
```

ผลต่างกันมากครับ — Prompt ที่ดีบอก 3 อย่าง: ภาษา, ความยาว, และโทน

### หลักการเขียน Prompt ที่ดี (RCTF Framework)

**R — Role: บอกว่าให้ Claude เป็นใคร**
```
"คุณคือนักบัญชีผู้เชี่ยวชาญ..."
"คุณคือครูสอนภาษาอังกฤษระดับมืออาชีพ..."
"คุณคือนักวิเคราะห์การลงทุนสายพื้นฐาน..."
```

**C — Context: บอกที่มาที่ไป**
```
"ผมเป็นเจ้าของร้านอาหาร มีพนักงาน 5 คน กำลังขยายสาขา..."
"นี่คือรายงานการเงินของบริษัท Q1/2026..."
"ลูกค้าของเราคือแม่บ้านอายุ 30-45 ปี..."
```

**T — Task: บอกว่าต้องการอะไร**
```
"ช่วยเขียนอีเมลตอบลูกค้าที่ร้องเรียนเรื่องสินค้าล่าช้า..."
"วิเคราะห์จุดแข็งจุดอ่อนของแผนธุรกิจนี้..."
"แปลเอกสารนี้จากอังกฤษเป็นไทย..."
```

**F — Format: บอกรูปแบบที่ต้องการ**
```
"ตอบเป็น bullet points 5 ข้อ"
"เขียนเป็นตาราง 3 คอลัมน์"
"ความยาวไม่เกิน 200 คำ"
"ใช้ภาษาทางการ ไม่ใช้ภาษาพูด"
```

**XML Template (Copy to use)**
```xml
<role>
คุณคือผู้เชี่ยวชาญด้าน
</role>

<context>
[ข้อมูลหรือเอกสารที่ต้องการให้ Claude อ่าน]
</context>

<instruction>
[คำสั่งที่ต้องการ]
</instruction>

<format>
ภาษาไทย กระชับ อ่านเข้าใจง่าย
</format>
```

### System Prompt vs User Prompt

```
System Prompt = "job description" ที่กำหนดบุคลิกและหน้าที่ของ Claude
              = บอกครั้งเดียว ใช้ตลอดการสนทนา

User Prompt   = งานที่มอบหมายแต่ละครั้ง
              = เปลี่ยนทุกครั้งตามงานที่ต้องการ
```

ตัวอย่างการใช้ร่วมกัน:
```
System: "คุณคือผู้ช่วยฝ่าย HR เชี่ยวชาญกฎหมายแรงงานไทย
        ตอบเป็นภาษาไทย ใช้ภาษาเป็นทางการ"

User: "พนักงานลาป่วยเกิน 30 วัน บริษัทมีสิทธิ์ทำอะไรได้บ้าง?"
```

## 3. Skill คืออะไร?

**Skill** คือ Prompt ที่เขียนไว้อย่างดี เก็บไว้ใช้ซ้ำได้ ติดตาม account ข้าม device

พูดง่ายๆ คือ แทนที่จะพิมพ์คำสั่งยาวๆ ซ้ำทุกครั้ง — เขียนครั้งเดียวแล้วเก็บไว้เป็น Skill ใช้ได้ตลอด

> ถ้า Prompt คือคำสั่งงานทั่วไป — Skill คือ "คู่มือการทำงาน" ที่เขียนละเอียดครั้งเดียว ใช้ได้ตลอด

### ความแตกต่างที่เห็นได้ชัด

```
แบบไม่มี Skill:
ทุกครั้งที่อยากสรุปเอกสาร → พิมพ์คำสั่งยาวๆ ใหม่
→ เสียเวลา → ผลลัพธ์ไม่สม่ำเสมอ

แบบมี Skill:
สร้าง Skill "document-summarizer" ครั้งเดียว
→ ทุกครั้งที่ต้องการ → เรียกใช้ทันที → ผลลัพธ์สม่ำเสมอทุกครั้ง
```

### ตัวอย่าง Skill จริงๆ

```
ชื่อ Skill: earnings-call-summarizer
ทำหน้าที่: สรุป Earnings Call เป็นโครงสร้าง 9 sections
ใช้เมื่อ: มี transcript Oppday ใหม่
ผลลัพธ์: Summary มาตรฐานทุกครั้ง ไม่ว่าใครจะใช้
```

### Skill เก็บไว้ที่ไหน และแชร์ได้ไหม

```
เก็บบน Anthropic server → ติดตาม account ทุก device
ดาวน์โหลดได้เป็น .skill file → จริงๆ คือ ZIP ที่มี Markdown ข้างใน
แชร์ให้คนอื่น import ได้ → ใครได้ไปก็ใช้ได้เหมือนกันทุกอย่าง
```

### เปรียบให้เห็นภาพ

```
Skill = สูตรอาหารที่เขียนไว้ดีแล้ว
ใครได้สูตรนี้ไป ทำตามแล้วได้ผลเหมือนกันทุกครั้ง
ไม่ต้องคิดใหม่ทุกครั้งที่ทำ
```

## 4. Tool คืออะไร?

**Tool** คือความสามารถที่ให้ Claude ทำสิ่งที่ AI ทำเองไม่ได้ — เข้าถึงโลกภายนอก

Claude เก่งมากในการคิดและเขียน แต่มีสิ่งที่ทำไม่ได้ด้วยตัวเอง เช่น ค้นหาข้อมูลจากอินเทอร์เน็ต ส่งอีเมล หรือดูราคาหุ้นตอนนี้ — Tool คือสิ่งที่แก้ปัญหานี้

> ถ้า Skill คือ "สอนให้คิดแบบไหน" — Tool คือ "ให้อุปกรณ์ที่ทำงานได้จริง"

### ความแตกต่างระหว่าง Skill กับ Tool

```
Skill = ข้อความ/Prompt → ทำให้ Claude ฉลาดขึ้นและตอบได้ดีขึ้น
Tool  = โค้ดที่รันได้จริง → ทำให้ Claude ทำสิ่งที่เป็นไปไม่ได้ให้เป็นไปได้
```

### ประเภทของ Tool

**Built-in Tools — ติดมากับ Claude.ai ใช้ได้เลย**
```
Web Search     → ค้นหาข้อมูลจากอินเทอร์เน็ตแบบ real-time
Code Execution → รันโค้ดได้จริงและแสดงผล
Image Analysis → วิเคราะห์และอธิบายรูปภาพ
File Reading   → อ่านและวิเคราะห์ไฟล์ที่แนบมา
```

**MCP Tools — ติดตั้งเพิ่มเองผ่าน Claude Desktop**
```
Gmail          → อ่าน/ส่งอีเมล
Google Calendar → ดู/เพิ่มนัดหมาย
LINE OA        → ส่งข้อความ LINE
Notion         → จัดการ workspace
Slack          → สื่อสารในทีม
Google Drive   → จัดการไฟล์บน cloud
```

### ข้อควรรู้เรื่อง Tool

Tool ต่างจาก Skill ตรงที่ต้องติดตั้งที่เครื่องครับ — ไม่ติดตาม account เหมือน Skill

```
Skill → เปิด claude.ai บนมือถือก็ใช้ได้เลย
Tool  → ต้องเปิด Claude Desktop บนเครื่องที่ติดตั้งไว้เท่านั้น
```

### เปรียบให้เห็นภาพ

```
Skill = สอนให้แพทย์เชี่ยวชาญด้านหัวใจ (ความรู้)
Tool  = ให้เครื่อง ECG ใช้ตรวจคนไข้ (อุปกรณ์)

แพทย์ที่เชี่ยวชาญ + มีเครื่องมือ = ทำงานได้ดีที่สุด
```

## 5. Artifacts คืออะไร?

**Artifacts** (อ่านว่า อาร์ติแฟคส์) คือผลลัพธ์ที่ Claude สร้างออกมาเป็น "ชิ้นงานจริง" ที่ใช้งานได้เลย ไม่ใช่แค่ข้อความในกล่องสนทนา

### ทำไมต้องมี Artifacts?

ปกติเวลาคุยกับ Claude — ได้แค่ข้อความใน chat อ่านแล้วต้อง copy ไปใช้เอง

Artifacts แตกต่างออกไปตรงที่ Claude สร้างไฟล์หรือ output ที่พร้อมใช้งานได้ทันทีใน chat นั้นเลย

```
ไม่มี Artifacts = ช่างบอกวิธีสร้างโต๊ะ
มี Artifacts    = ช่างสร้างโต๊ะให้เสร็จแล้ววางตรงหน้าคุณ
```

### Artifacts ทำอะไรได้บ้าง

**HTML / เว็บเพจ**
```
สั่งให้สร้าง Landing Page
→ ได้หน้าเว็บที่เปิดดูได้ทันทีใน chat
→ ไม่ต้องมีความรู้ HTML เลย
```

**โค้ด (Python, JavaScript, PHP ฯลฯ)**
```
สั่งให้เขียนโปรแกรม
→ ได้โค้ดพร้อม copy ไปใช้ได้เลย
→ มี syntax highlighting อ่านง่าย
```

**Markdown / เอกสาร**
```
สั่งให้เขียนรายงาน
→ ได้เอกสารที่จัดรูปแบบสวยงาม
→ Export เป็นไฟล์ได้ทันที
```

**SVG / รูปภาพ**
```
สั่งให้สร้าง diagram หรือ chart
→ ได้รูปภาพออกมาเลย
→ แก้ไขได้ง่ายเพราะเป็นโค้ด
```

### วิธีใช้ Artifacts

ไม่ต้องทำอะไรพิเศษครับ แค่สั่งให้ Claude สร้างสิ่งที่ต้องการ — Claude จะตัดสินใจเองว่าควรสร้างเป็น Artifact หรือไม่

```
"สร้าง Landing Page สำหรับร้านกาแฟของฉัน"
→ Claude สร้าง HTML ให้เห็นทันทีใน chat

"เขียน Python script อ่านไฟล์ CSV"
→ Claude สร้างโค้ดเป็น Artifact ให้ copy ได้เลย
```

### เปรียบให้เห็นภาพ

```
Chat ปกติ = คุยโทรศัพท์กับช่าง ได้แค่คำแนะนำ
Artifacts = ช่างส่งงานสำเร็จมาให้ถึงบ้าน
```

## 6. Agent คืออะไร?

**Agent** คือ AI ที่รับเป้าหมาย แล้วคิดและลงมือทำเองหลาย step โดยไม่ต้องให้คนสั่งทุกขั้น

นี่คือการยกระดับจาก "ถาม-ตอบ" ไปสู่ "รับงานแล้วทำจนเสร็จ"

> ถ้า Claude ใน chat คือ "ที่ปรึกษา" — Agent คือ "พนักงานที่รับงานแล้วทำจนเสร็จเอง"

### ความแตกต่างระหว่าง Chat ปกติ กับ Agent

| | Claude ใน Chat | Agent |
|---|---|---|
| การทำงาน | ถาม-ตอบ วนซ้ำ | รับงาน → คิด → ทำ → รายงาน |
| ผู้ควบคุม Flow | มนุษย์สั่งทุก step | AI ตัดสินใจเอง |
| ใช้ Tools | ไม่จำเป็น | หัวใจหลัก |
| ตัวอย่าง | "ช่วยสรุปนี้หน่อย" | "สรุป Oppday ทุกบริษัทแล้วส่ง LINE" |

### องค์ประกอบของ Agent ที่ดี

```
1. เป้าหมาย       → รู้ว่าต้องทำอะไร
2. Tools          → มีอุปกรณ์ทำงานได้จริง
3. Logic          → รู้ว่าทำขั้นตอนไหนก่อน-หลัง
4. Error handling → รับมือเมื่อมีปัญหา
5. Output         → ส่งผลลัพธ์ออกมาในรูปแบบที่ต้องการ
```

### Agent สร้างได้จากอะไร

```
Python (.py)     → ยืดหยุ่นที่สุด ควบคุมได้เต็มที่
JavaScript (.js) → รันบน Node.js
Claude Code      → รันบน terminal ใช้ Pro account
n8n / Make       → No-code ลากวางได้เลย
```

### ตัวอย่าง Agent จริงๆ

```
oppday_agent.py:
รับ:    โฟลเดอร์ที่มีไฟล์ transcript .txt
ทำ:     อ่านไฟล์ → detect ticker → สรุปด้วย Claude API → บันทึก .md
ข้าม:   ไฟล์ที่สรุปแล้ว (ไม่ทำซ้ำ)
รายงาน: สรุปผลว่าทำกี่ไฟล์ ข้ามกี่ไฟล์ ใช้เวลาเท่าไหร่
```

### เปรียบให้เห็นภาพ

```
Chat ปกติ = โทรถามที่ปรึกษาทุกครั้งที่มีคำถาม
Agent     = จ้างพนักงานประจำที่รับงานแล้วทำจนเสร็จเอง
           ไม่ต้องคอยสั่งทุก step
```

## 7. Memory คืออะไร?

**Memory** คือความสามารถให้ Claude จำข้อมูลข้ามการสนทนาได้

ปัญหาหลักของ Claude คือทุก chat ใหม่ = เริ่มใหม่หมด จำอะไรจากครั้งก่อนไม่ได้เลย Memory คือวิธีแก้ปัญหานี้

### Memory 4 ประเภท

**1. In-context Memory — จำในการสนทนาเดียวกัน**
```
เก็บข้อมูลไว้ใน messages ที่ส่งไปพร้อมกัน
ข้อดี:  ง่ายมาก ไม่ต้องทำอะไรพิเศษ
ข้อเสีย: หายทันทีเมื่อปิด chat
เหมาะกับ: งานในครั้งเดียว ไม่ต้องการความต่อเนื่อง
```

**2. External Memory — บันทึกไว้ในไฟล์ (แนะนำที่สุด)**
```
บันทึกลงไฟล์ .json แล้วโหลดกลับมาทุกครั้ง
ข้อดี:  จำได้ถาวร ข้ามครั้งได้ ข้าม device ได้
ข้อเสีย: ต้อง paste เองเมื่อเริ่ม session ใหม่
เหมาะกับ: วิเคราะห์หุ้นต่อเนื่อง, project ยาว
```

**3. Summary Memory — สรุปไว้แล้วเก็บ**
```
สรุปการสนทนาก่อนหน้าเก็บไว้ ไม่เก็บทุกอย่าง
ข้อดี:  ประหยัด token กว่าเก็บทั้งหมด
ข้อเสีย: อาจตกหล่นรายละเอียดบางอย่าง
เหมาะกับ: conversation ยาวที่ต้องการต่อเนื่อง
```

**4. RAG — ค้นหาในเอกสารเยอะๆ**
```
เก็บเอกสารจำนวนมาก ดึงเฉพาะส่วนที่เกี่ยวข้องมาใช้
ข้อดี:  รองรับข้อมูลมหาศาล ไม่จำกัด
ข้อเสีย: ต้องตั้งค่าระบบ มีความซับซ้อน
เหมาะกับ: knowledge base ขนาดใหญ่
```

### วิธีใช้ External Memory ใน Chat ง่ายๆ

```
ขั้นที่ 1 — ก่อนปิด chat:
"สรุปสิ่งที่คุยไปทั้งหมดเป็น JSON ให้หน่อย"

ขั้นที่ 2 — Copy JSON ที่ได้เก็บไว้:
ใน Notion, Obsidian, หรือไฟล์ .json บนเครื่อง

ขั้นที่ 3 — ครั้งหน้าเปิด chat ใหม่:
Paste JSON + "นี่คือ context เดิม คุยต่อได้เลย"
```

### ตัวอย่าง Memory JSON สำหรับการวิเคราะห์หุ้น

```json
  "ticker": "BEM",
  "last_updated": "2026-06-10",
```

## 8. Multi-agent คืออะไร?

**Multi-agent** คือการใช้ Agent หลายตัวทำงานร่วมกัน แต่ละตัวเชี่ยวชาญคนละด้าน

แทนที่จะให้ Agent เดียวทำทุกอย่าง — แบ่งงานให้ทีมทำ แต่ละคนโฟกัสสิ่งที่ตัวเองถนัด

> เหมือนบริษัทที่มีพนักงานหลายคน แทนที่จะให้คนเดียวทำทุกอย่าง

### 3 Pattern หลัก

**1. Sequential — ทำต่อกันเป็นสาย**
```
Agent 1 (ดึงข้อมูล) → Agent 2 (วิเคราะห์) → Agent 3 (รายงาน)
เหมาะกับ: งานที่ต้องทำตามลำดับขั้นตอน
```

**2. Parallel — ทำพร้อมกัน**
```
Agent 1 ─┐
Agent 2 ─┼→ Agent รวมผล → Output
Agent 3 ─┘
เหมาะกับ: งานที่แบ่งแยกได้ อยากประหยัดเวลา
```

**3. Supervisor — มีหัวหน้าคุม**
```
Supervisor Agent
├── สั่ง Agent 1 → รับผล
├── สั่ง Agent 2 → รับผล
└── รวมผลและตัดสินใจขั้นสุดท้าย
เหมาะกับ: งานซับซ้อนที่ต้องการการตัดสินใจหลายชั้น
```

### Agent แต่ละตัวรู้ได้ไงว่าต้องทำงานต่อจากใคร

```
Agent ไม่รู้จักกันเลย — โค้ดเป็นคนส่งงานต่อให้

เหมือนสายพานการผลิต:
พนักงานแต่ละคนรู้แค่ว่า "รับงานจากซ้าย ส่งงานไปขวา"
ไม่รู้ว่าสายพานมีกี่ขั้น ใครเป็นคนต่อไป
```

### เมื่อไหรควรใช้ Multi-agent

```
✅ งานช้าเกินไป → แยกทำ Parallel ประหยัดเวลา
✅ งานซับซ้อนจนคุณภาพลด → แยกให้แต่ละตัวโฟกัส
✅ อยากเพิ่มงานใหม่โดยไม่แตะโค้ดเดิม

❌ งานง่ายๆ flow ตายตัว → Agent เดียวพอ ไม่ต้องซับซ้อน
❌ งานที่ทำได้ดีอยู่แล้ว → ไม่จำเป็นต้องแยก
```

## 9. ภาพรวมทั้งหมด: ทุกอย่างเชื่อมกันอย่างไร

### แผนผังความสัมพันธ์

```
┌─────────────────────────────────────────────────────┐
│                      CLAUDE                          │
│                                                      │
│  Prompt ──→ Skill ──→ บอกให้คิดแบบไหน              │
│  Tool  ──→ ทำสิ่งที่ AI ทำเองไม่ได้                 │
│  Artifacts ──→ สร้างผลงานจริงให้ใช้งานได้เลย        │
│  Memory ──→ จำข้อมูลข้ามครั้ง                       │
│                                                      │
└─────────────────────────────────────────────────────┘
                ↓ รวมกันเป็น
┌─────────────────────────────────────────────────────┐
│                      AGENT                           │
│  รับเป้าหมาย → คิดเอง → ใช้ Tool → ทำจนเสร็จ       │
└─────────────────────────────────────────────────────┘
                ↓ หลายตัวรวมกันเป็น
┌─────────────────────────────────────────────────────┐
│               MULTI-AGENT SYSTEM                     │
│  Agent 1 + Agent 2 + Agent 3 → งานซับซ้อน           │
└─────────────────────────────────────────────────────┘
```

### สรุปเปรียบเทียบทุกอย่าง

| สิ่ง | คืออะไร | เก็บที่ไหน | ใครควรใช้ |
|---|---|---|---|
| Prompt | คำสั่งให้ Claude | ในหัว / ในโค้ด | ทุกคน |
| Skill | Prompt ที่เก็บไว้ดีๆ | Anthropic server | ใช้ Claude.ai บ่อย |
| Tool | โค้ดที่รันได้จริง | เครื่องตัวเอง | มี Claude Desktop |
| Artifacts | ผลงานพร้อมใช้ใน chat | ใน chat | ทุกคน |
| Agent | ระบบที่ทำงานอัตโนมัติ | เครื่องตัวเอง | นักพัฒนา |
| Memory | วิธีให้ Claude จำข้อมูล | ไฟล์ / DB | งานต่อเนื่อง |
| Multi-agent | หลาย Agent ทำงานร่วมกัน | เครื่องตัวเอง | งานซับซ้อน |

**Use Case 1: เขียนอีเมลและเอกสารทางการ** ⭐

เครื่องมือ: Claude.ai chat

```

ประหยัดเวลา: 30 นาที → 2 นาที
```

**Use Case 6: วิเคราะห์รูปภาพและเอกสารด้วย Vision** ⭐⭐

เครื่องมือ: Claude.ai chat + อัปโหลดรูปภาพ

```
Claude มองเห็นและวิเคราะห์รูปภาพได้โดยตรง
ไม่ต้องพิมพ์อธิบายรูป แค่แนบมาแล้วถามได้เลย

สถานการณ์ที่ใช้บ่อย:

1. ถ่ายรูปใบเสร็จ/บิล → สกัดข้อมูลเป็นตาราง
"นี่คือใบเสร็จค่าใช้จ่ายจากทริปนี้
สกัดข้อมูลออกมาเป็นตาราง: วันที่ รายการ จำนวนเงิน
แล้วสรุปค่าใช้จ่ายรวมแต่ละหมวด"

2. ถ่ายรูป UI ที่วาดบนกระดาษ → สร้างเป็นเว็บจริง
"นี่คือ wireframe หน้า Login ที่วาดมือ
สร้าง HTML ตามดีไซน์นี้ให้หน่อย"
→ Claude แปลงภาพวาดมือเป็นโค้ดทันที

3. ถ่ายรูปกราฟหรือตารางในเอกสาร → วิเคราะห์ข้อมูล
"นี่คือกราฟยอดขายจากรายงานประจำปี
วิเคราะห์ trend และบอก insight 3 ข้อ"

4. ถ่ายรูปนามบัตร → แปลงเป็นข้อมูล contact
"แปลงข้อมูลนามบัตรนี้เป็น JSON"

ผลลัพธ์: ไม่ต้องพิมพ์ข้อมูลซ้ำ แค่ถ่ายรูปแล้วถามได้เลย
```

## 12. Token & Context Window

### Token คืออะไร?

**Token** คือหน่วยที่ Claude ใช้อ่านและเขียนข้อความ — ไม่ใช่คำ ไม่ใช่ตัวอักษร แต่เป็น "ชิ้นส่วนของภาษา"

```
ภาษาอังกฤษ:
"Hello world" = 2 tokens (1 คำ ≈ 1 token)

ภาษาไทย:
"สวัสดีครับ" = ประมาณ 8-12 tokens
(ภาษาไทยใช้ token มากกว่าอังกฤษ 3-4 เท่า)
```

### ทำไม Token ถึงสำคัญ?

Token มีผลต่อ 2 อย่างหลักๆ:

**ราคา**
```
API คิดเงินตาม token ที่ใช้
Input tokens  = token ที่คุณส่งให้ Claude
Output tokens = token ที่ Claude ตอบกลับ
ยิ่งใช้มาก ยิ่งจ่ายมาก
```

**ข้อจำกัด**
```
Claude รับ input ได้ไม่เกินจำนวน token ที่กำหนด
เกินนั้น → Claude อ่านไม่ครบ หรือตอบผิดพลาด
```

### Context Window คืออะไร?

**Context Window** คือ "ความจำระยะสั้น" ของ Claude — มีขนาดจำกัด

```
เปรียบเหมือนโต๊ะทำงาน:
โต๊ะเล็ก → วางของได้น้อย ต้องเอาของเก่าออกก่อน
โต๊ะใหญ่ → วางของได้มาก ทำงานหลายอย่างพร้อมกันได้

Context Window = ขนาดโต๊ะ
ทุกอย่างใน chat = ของบนโต๊ะ
```

ขนาด Context Window ของ Claude ปัจจุบัน:
```
Claude Sonnet / Opus → ~200,000 tokens
≈ หนังสือประมาณ 150-200 หน้า
```

### ผลกระทบในการใช้งานจริง

**ปัญหาที่พบบ่อย:**
```
❌ Claude ลืมสิ่งที่คุยไว้ตอนต้น chat
   → เพราะ context เต็ม ของเก่าถูกดันออก

❌ Claude ตอบแปลกๆ เมื่อส่งไฟล์ใหญ่
   → เพราะไฟล์กินพื้นที่ context จนเหลือน้อยมาก

❌ Agent batch ใช้เงินเยอะมาก
   → เพราะส่ง transcript ทุกไฟล์รวมกันใน context เดียว
```

**วิธีรับมือ:**
```
✅ แบ่งเอกสารยาวๆ ออกเป็นส่วนๆ
✅ เริ่ม chat ใหม่เมื่อ conversation ยาวเกินไป
✅ ใช้ RAG แทนการส่งเอกสารทั้งหมด
✅ สรุป chat เก่าแล้ว paste เข้า chat ใหม่
```

### Use Case: วิเคราะห์สัญญาธุรกิจยาวอย่างถูกวิธี

```
สถานการณ์: ได้รับสัญญา 80 หน้า กลัว context เต็ม

วิธีที่ถูกต้อง — แบ่งเป็น section แล้วถามทีละส่วน:

"วิเคราะห์ section 1-3 นี้: [paste]
เน้นเรื่อง: เงื่อนไขการชำระเงินและ penalty"

"วิเคราะห์ section 4-6 นี้: [paste]
เน้นเรื่อง: เงื่อนไขการยกเลิกสัญญา"

ผลลัพธ์: วิเคราะห์ได้ครบ แม่นยำกว่า
         ไม่เสี่ยงกับปัญหา context เต็ม
```

## 13. Hallucination และวิธีรับมือ

### Hallucination คืออะไร?

**Hallucination** คือเมื่อ Claude ตอบข้อมูลที่ผิด แต่ฟังดูมั่นใจมาก ราวกับว่าเป็นความจริง

ชื่อนี้มาจากอาการประสาทหลอน — เห็นสิ่งที่ไม่มีอยู่จริง แต่เชื่อว่ามีจริง

```
ตัวอย่าง Hallucination:
คุณ:   "บริษัท XYZ จดทะเบียนเมื่อปีไหน?"
Claude: "บริษัท XYZ จดทะเบียนเมื่อปี 2543 ครับ"
        (ตอบมั่นใจมาก แต่ตัวเลขผิด หรืออาจไม่มีบริษัทนี้เลย)
```

### ทำไม Claude ถึง Hallucinate?

Claude ไม่ได้ "ค้นหาข้อมูล" จริงๆ — มันทำนายคำถัดไปจากสิ่งที่เรียนรู้มา เหมือนเดาคำที่น่าจะมาต่อ บางครั้งจึงเดาผิดแต่ฟังดูถูก

### สังเกต Hallucination ได้อย่างไร?

```
⚠️ ตัวเลขที่แม่นยำมากผิดปกติ เช่น วันที่ เวลา สถิติ
⚠️ ชื่อคน บริษัท หรือสถานที่ที่ไม่คุ้น
⚠️ การอ้างอิงแหล่งข้อมูลที่ฟังดูดีมากแต่ตรวจสอบไม่ได้
⚠️ Claude ตอบโดยไม่บอกว่าไม่แน่ใจเลย
```

### วิธีรับมือและป้องกัน

**1. บอกให้ Claude ยอมรับเมื่อไม่รู้**
```
เพิ่มใน Prompt:
"ถ้าไม่แน่ใจเรื่องไหน ให้บอกว่าไม่แน่ใจ
ห้ามเดาหรือสร้างข้อมูลขึ้นมาเอง"
```

**2. ให้ข้อมูลไปเองแทนให้ Claude จำ**
```
แทนที่จะถาม: "ราคาหุ้น PTT วันนี้เท่าไหร่"
ทำแบบนี้แทน: "ราคาหุ้น PTT วันนี้คือ 35.50 บาท
              วิเคราะห์ว่าควรซื้อหรือรอ"
```

**3. ใช้ Web Search สำหรับข้อมูล real-time**
```
เปิด Web Search ใน Claude.ai
แล้วถามข้อมูลที่ต้องการความแม่นยำสูง
Claude จะค้นหาจริงๆ แทนการเดา
```

**4. เช็คข้อมูลสำคัญเสมอ**
```
ข้อมูลที่ควรเช็คก่อนนำไปใช้:
- ตัวเลขทางการเงิน
- กฎหมายและระเบียบ
- ข้อมูลทางการแพทย์
- การอ้างอิงแหล่งข้อมูล
```

### Use Case: ตรวจสัญญาเช่าก่อนเซ็น

```
สถานการณ์: อยากให้ Claude ตรวจสัญญาเช่าออฟฟิศ
กลัวว่า Claude จะ hallucinate เรื่องกฎหมาย

Prompt ที่ถูกต้อง:
"ตรวจสัญญาเช่านี้ให้หน่อย: [paste สัญญา]
สิ่งที่ต้องการ:
1. ข้อไหนที่ดูผิดปกติหรือไม่เป็นธรรม
2. ข้อไหนที่ควรต่อรองเพิ่ม
หมายเหตุ: ถ้าไม่แน่ใจเรื่องกฎหมาย ให้บอกว่าควรปรึกษาทนาย
อย่าตอบข้อมูลที่ไม่มีอยู่ในสัญญานี้"

ผลลัพธ์: ได้ข้อมูลที่เชื่อถือได้
         รู้ว่าส่วนไหนต้องเช็คเพิ่มกับผู้เชี่ยวชาญ
```


### อะไรที่ไม่ควรส่งให้ Claude

```
❌ รหัสผ่าน และ API Keys
❌ เลขบัตรประชาชน หนังสือเดินทาง
❌ ข้อมูลการเงินส่วนตัว เช่น เลขบัญชี
❌ ข้อมูลลูกค้าที่มีข้อมูลส่วนบุคคล (PDPA)
❌ ความลับทางการค้าของบริษัท (ถ้าใช้ Free/Pro)
❌ ข้อมูลทางการแพทย์ของผู้ป่วย
```

### วิธีใช้ Claude อย่างปลอดภัยในองค์กร

**Anonymize ข้อมูลก่อนส่ง**
```
แทนที่จะส่ง:
"นายสมชาย อายุ 45 ป่วยเป็นเบาหวาน ..."

ส่งแบบนี้แทน:
"ผู้ป่วยชาย อายุ 40-50 ป่วยเป็นเบาหวาน ..."
```

**ใช้ข้อมูลตัวอย่างแทน**
```
แทนที่จะส่งสัญญาจริง
→ ส่งสัญญาตัวอย่างที่ลบข้อมูลสำคัญออกแล้ว
→ ขอให้ Claude สร้าง template ให้
```

**ตั้งค่า Privacy ใน Claude.ai**
```
Settings → Data & Privacy
→ ปิด "Improve Claude for everyone"
เพื่อไม่ให้ conversation นำไป train model
```

### Use Case: วิเคราะห์ข้อมูล HR อย่างปลอดภัย

```
ผลลัพธ์: ได้ insight ที่ต้องการ
         โดยไม่เปิดเผยข้อมูลส่วนบุคคล
```

## 15. ไฟล์คำสั่งเบื้องหลัง (CLAUDE.md, System Prompt)

### หลักการของไฟล์ประเภทนี้

ในการใช้ Claude ทั่วไป เราพิมพ์คำสั่งทุกครั้งที่ต้องการ แต่มีวิธีที่ฉลาดกว่า — เขียนคำสั่งไว้ในไฟล์ แล้วให้ Claude อ่านอัตโนมัติก่อนทำงาน

```
วิธีปกติ:
ทุกครั้งที่คุย → พิมพ์คำสั่งใหม่ → เสียเวลา → ผลลัพธ์ไม่สม่ำเสมอ

ใช้ไฟล์คำสั่ง:
เขียนครั้งเดียว → Claude อ่านอัตโนมัติ → สม่ำเสมอทุกครั้ง
```

### CLAUDE.md — ใช้กับ Claude Code

**CLAUDE.md** คือไฟล์ที่วางไว้ใน project folder เพื่อบอก Claude Code ว่า project นี้คืออะไร

```
Claude Code อ่าน CLAUDE.md ทุกครั้งที่เปิด project
เหมือน "briefing เอกสาร" ที่พนักงานใหม่ต้องอ่านวันแรก
```

ตัวอย่าง CLAUDE.md:
```markdown
# Project: oppday-summarizer

## วัตถุประสงค์
สรุป Earnings Call transcript เป็น Markdown summary

## โครงสร้างไฟล์
- /raw     → transcript .txt ต้นฉบับ
- /summary → ไฟล์ .md ที่สรุปแล้ว

## กฎที่ต้องทำตาม
- ภาษาไทยเสมอ ยกเว้น technical term
- ชื่อไฟล์ output: TICKER_YYYYQn_EarningCallSummary.md
- ห้ามเขียนทับไฟล์ที่มีอยู่แล้ว
```

### System Prompt ใน Project — ใช้กับ Claude.ai

**System Prompt ใน Project** คือคำสั่งที่ทำงานอยู่เบื้องหลังทุก chat ใน Project นั้น

```
สร้าง Project "งาน HR"
ใส่ System Prompt:
"คุณคือผู้ช่วยฝ่าย HR เชี่ยวชาญกฎหมายแรงงานไทย
ตอบภาษาไทยเสมอ ใช้ภาษาทางการ
ถ้าไม่แน่ใจเรื่องกฎหมาย ให้แนะนำปรึกษาผู้เชี่ยวชาญ"

ผลลัพธ์:
ทุก chat ใน Project นี้ → Claude เป็น HR specialist อัตโนมัติ
ไม่ต้องพิมพ์คำสั่งซ้ำทุกครั้ง
```

### ความสัมพันธ์ระหว่างไฟล์ต่างๆ

```
CLAUDE.md      → ใช้กับ Claude Code บน terminal
System Prompt  → ใช้กับ Claude.ai ใน Project
SKILL.md       → ใช้กับ Claude.ai เป็น Skill
```

### Use Case: ตั้งค่า Project สำหรับทีม Marketing

```
สถานการณ์: ทีม Marketing 5 คนใช้ Claude ร่วมกัน
อยากให้ผลลัพธ์ consistent ทุกคน

วิธีทำ:
1. สร้าง Project "Marketing Team" ใน Claude.ai
2. ใส่ System Prompt:
   "คุณคือ Marketing Specialist ของบริษัท [ชื่อ]
   สินค้าหลัก: [อธิบาย] กลุ่มเป้าหมาย: [อธิบาย]
   Tone: เป็นมิตร ทันสมัย ไม่เป็นทางการเกินไป"
3. แชร์ Project ให้ทีมทั้ง 5 คน

ผลลัพธ์: ทุกคนในทีมได้ output ที่ consistent
         ลดเวลาเขียน brief จาก 1 ชั่วโมง → 5 นาที
```

## 16. Prompt Engineering เชิงลึก

### ทำไมต้องเรียนรู้เพิ่มจาก Part 1?

Prompt พื้นฐานใน Part 1 ทำงานได้ดีสำหรับงานทั่วไป แต่ถ้าต้องการผลลัพธ์ที่แม่นยำและสม่ำเสมอกว่านี้ — มี technique เพิ่มเติมที่ช่วยได้มากครับ

### Technique 1: Chain of Thought (CoT)

**Chain of Thought** คือการบอกให้ Claude คิดทีละขั้นก่อนตอบ แทนที่จะตอบทันที

```
แบบปกติ:
"ราคาหุ้น A คือ 100 บาท ขึ้น 5% แล้วลง 3% ราคาสุดท้ายเท่าไหร่"
→ Claude อาจคำนวณผิด

แบบ Chain of Thought:
"คิดทีละขั้นตอน แสดงการคำนวณทุกขั้น แล้วค่อยบอกราคาสุดท้าย
ราคาหุ้น A คือ 100 บาท ขึ้น 5% แล้วลง 3%"
→ Claude คิดละเอียดขึ้น ผิดพลาดน้อยลง
```

เหมาะกับ: คณิตศาสตร์, logic, การตัดสินใจซับซ้อน

### Technique 2: Few-shot Examples

**Few-shot** คือการให้ตัวอย่าง input-output ก่อน แล้วให้ Claude ทำแบบเดียวกัน

```
"แปลง feedback ลูกค้าเป็น action item ตามตัวอย่างนี้:

ตัวอย่าง 1:
Input:  'ส่งของช้ามาก รอ 2 อาทิตย์'
Output: [โลจิสติกส์] ตรวจสอบและปรับปรุงระยะเวลาจัดส่ง

ตัวอย่าง 2:
Input:  'พนักงานไม่สุภาพ'
Output: [HR] อบรมมารยาทการบริการลูกค้า

ตอนนี้แปลงนี้ให้หน่อย:
'เว็บไซต์ใช้งานยาก หาสินค้าไม่เจอ'"
```

เหมาะกับ: งานที่ต้องการ output รูปแบบเฉพาะ

### Technique 3: Negative Prompting

บอก Claude ว่า "ไม่ต้องการอะไร" ชัดเจนเท่ากับบอกว่า "ต้องการอะไร"

```
"เขียนบทความเรื่องการลงทุนในหุ้น
ห้าม: ใช้คำว่า 'รับประกัน' หรือ 'แน่นอน'
ห้าม: แนะนำหุ้นตัวใดตัวหนึ่งโดยตรง
ห้าม: ใช้ศัพท์เทคนิคโดยไม่อธิบาย"
```

### Technique 4: Output Format ที่แม่นยำ

กำหนด format ให้ชัดเจนมากขึ้น โดยเฉพาะเมื่อต้องนำไปใช้ต่อ

```
"วิเคราะห์คู่แข่งและตอบใน JSON format นี้เท่านั้น:
{
  'company': 'ชื่อบริษัท',
  'strengths': ['จุดแข็ง 1', 'จุดแข็ง 2'],
  'weaknesses': ['จุดอ่อน 1'],
  'threat_level': 'สูง/กลาง/ต่ำ'
}"
```

### Technique 5: Iterative Refinement

ไม่ต้องได้ output สมบูรณ์ในครั้งเดียว — ทำซ้ำและปรับปรุง

```
ครั้งที่ 1: "เขียนบทนำบทความเรื่องนี้"
ครั้งที่ 2: "ดีแล้ว แต่ขอให้น่าสนใจขึ้น เพิ่ม hook ตอนต้น"
ครั้งที่ 3: "ดีมาก แต่ขอให้สั้นลง 30% โดยไม่เสียใจความ"
```

### Technique 6: XML Tags — วิธีที่ Anthropic แนะนำอย่างเป็นทางการ

**XML Tags** คือการใช้แท็กเพื่อแบ่งส่วนของ Prompt ให้ชัดเจน Claude อ่านและแยกแยะได้ดีขึ้นมาก

```
XML Tag คืออะไร?
<ชื่อ> เนื้อหา </ชื่อ>
เหมือนกล่องที่มีป้ายชื่อ — Claude รู้ทันทีว่าส่วนไหนคืออะไร
```

**แบบไม่มี XML Tags — Claude ต้องเดาเองว่าอะไรคืออะไร:**
```
คุณคือนักวิเคราะห์การเงิน นี่คือข้อมูลบริษัท รายได้ 100 ล้าน
กำไร 20 ล้าน หนี้ 50 ล้าน วิเคราะห์และเปรียบเทียบกับ
ปีที่แล้วที่รายได้ 80 ล้าน กำไร 15 ล้าน หนี้ 60 ล้าน
ตอบเป็นภาษาไทย ไม่เกิน 5 บรรทัด
```

**แบบมี XML Tags — Claude เข้าใจโครงสร้างทันที:**
```xml
<role>คุณคือนักวิเคราะห์การเงินมืออาชีพ</role>

<data_current_year>
รายได้: 100 ล้านบาท
กำไร: 20 ล้านบาท
หนี้: 50 ล้านบาท
</data_current_year>

<data_last_year>
รายได้: 80 ล้านบาท
กำไร: 15 ล้านบาท
หนี้: 60 ล้านบาท
</data_last_year>

<instruction>
วิเคราะห์และเปรียบเทียบผลประกอบการ 2 ปี
</instruction>

<format>ภาษาไทย ไม่เกิน 5 บรรทัด</format>
```

**ประโยชน์ของ XML Tags:**
```
✅ Claude แยกแยะ context, คำสั่ง, และข้อมูลออกจากกันชัดเจน
✅ ผลลัพธ์แม่นยำและสม่ำเสมอกว่า
✅ ลด token ที่ต้องใช้ในการอธิบายโครงสร้าง
✅ เมื่อ Prompt ยาวมาก XML Tags ช่วยให้ Claude ไม่ "หลงทาง"
```

**XML Tags ที่ใช้บ่อย:**
```xml
<role>        → บอกว่า Claude เป็นใคร
<context>     → ข้อมูลพื้นหลัง
<instruction> → คำสั่งที่ต้องการ
<example>     → ตัวอย่าง input/output
<data>        → ข้อมูลที่ต้องวิเคราะห์
<format>      → รูปแบบที่ต้องการ
<constraint>  → ข้อจำกัด/สิ่งที่ห้ามทำ
```

### Use Case: สร้าง Template รายงาน KPI ที่ใช้ซ้ำได้

```
สถานการณ์: ต้องรายงาน KPI ให้ผู้บริหารทุกเดือน
อยากได้ format เดิมทุกครั้ง

ใช้ Few-shot + Output Format:
"นี่คือตัวอย่างรายงาน KPI แบบที่ต้องการ:
[paste ตัวอย่างรายงานที่ชอบ]

สร้างรายงานในรูปแบบเดียวกันจากข้อมูลเดือนนี้:
[paste data]"

ผลลัพธ์: รายงานที่ consistent ทุกเดือน
         ไม่ต้องปรับ format ทุกครั้ง
```

## 17. Project ใน Claude.ai

### Project คืออะไร และต่างจาก Chat ปกติยังไง?

**Project** คือ workspace ที่มี context ร่วมกัน — ไม่ใช่แค่ folder เก็บ chat

```
Chat ปกติ:
เปิด chat ใหม่ทุกครั้ง → Claude ไม่จำอะไรเลย
ต้องอธิบาย context ใหม่ทุกครั้ง

Project:
Claude จำ context ของ Project นี้ตลอด
ทุก chat ใน Project → Claude รู้ว่ากำลังทำงานอะไร สำหรับใคร
```

### ทำไมต้องใช้ Project?

```
✅ ไม่ต้องพิมพ์ context ซ้ำทุกครั้ง
✅ ผลลัพธ์สม่ำเสมอทุก chat
✅ แชร์ให้ทีมใช้ร่วมกันได้ (Team/Enterprise plan)
✅ อัปโหลดเอกสารไว้ให้ Claude อ่านได้ตลอด
✅ จัดระเบียบงานหลายประเภทแยกจากกัน
```

### วิธีตั้งค่า Project ให้มีประสิทธิภาพ

**ขั้นที่ 1 — สร้าง Project ตาม "บทบาท" ไม่ใช่ "งาน"**
```
❌ แบบผิด: สร้าง Project ใหม่ทุกครั้งที่มีงาน
   "Project รายงานเดือนมกรา"
   "Project รายงานเดือนกุมภา"

✅ แบบถูก: สร้างตาม domain หรือบทบาท
   "งานการเงิน"
   "งาน Marketing"
   "การลงทุนส่วนตัว"
```

**ขั้นที่ 2 — เขียน System Prompt ที่ดี**
```
บอกให้ครบ 4 อย่าง:
1. Claude เป็นใคร / ผู้เชี่ยวชาญด้านไหน
2. บริบทของงาน / บริษัท
3. กลุ่มเป้าหมายของ output
4. สไตล์และรูปแบบที่ต้องการ
```

**ขั้นที่ 3 — อัปโหลดเอกสารอ้างอิง**
```
Claude อ่านเอกสารเหล่านี้ได้ตลอดใน Project:
- นโยบายบริษัท
- price list สินค้า
- template ที่ใช้บ่อย
```

### ข้อผิดพลาดที่มือใหม่มักทำ

```
❌ ใช้ Project เหมือน folder เก็บ chat
   → จริงๆ ต้องตั้งค่า System Prompt ด้วย

❌ สร้าง Project เดียวใช้ทุกอย่าง
   → ควรแยกตาม domain เพื่อให้ context ชัดเจน

❌ ไม่อัปเดต System Prompt เมื่องานเปลี่ยน
   → ควรรีวิว System Prompt ทุก 1-2 เดือน

❌ คาดหวังว่า Project จะจำทุก conversation
   → Project จำ System Prompt และเอกสาร
     แต่ไม่ได้จำทุก chat โดยอัตโนมัติ
```

### Use Case: Project สำหรับทีมขาย

```
สถานการณ์: ทีมขาย 10 คน ต้องเขียน proposal
อยากให้ออกมา consistent ทุกคน

วิธีทำ:
1. สร้าง Project "Sales Team"
2. System Prompt:
   "คุณคือผู้เชี่ยวชาญด้านการขายของ [บริษัท]
   สินค้า: [อธิบาย] จุดเด่น: [USP 3 ข้อ]
   โทน: มืออาชีพ น่าเชื่อถือ แต่ไม่แข็งกร้าว"
3. อัปโหลด: price list, case studies, template proposal
4. แชร์ให้ทีมทั้ง 10 คน

ผลลัพธ์: ทุกคนเขียน proposal ได้คุณภาพเดียวกัน
         ลดเวลาเขียนจาก 2 ชั่วโมง → 20 นาที
```

## 18. Claude Desktop + MCP

### Claude Desktop คืออะไร?

**Claude Desktop** คือแอปพลิเคชันสำหรับ Mac และ Windows ที่ให้ Claude ทำงานกับเครื่องคอมพิวเตอร์ของคุณได้โดยตรง

```
Claude.ai (เว็บ/มือถือ):
คุย chat ได้ แต่เข้าถึงไฟล์หรือแอปบนเครื่องไม่ได้

Claude Desktop:
Claude เชื่อมต่อกับเครื่องคุณได้โดยตรง
อ่านไฟล์, ส่งอีเมล, ดู calendar ได้จริงๆ
```

### MCP คืออะไร?

**MCP** ย่อมาจาก **Model Context Protocol** — มาตรฐานที่ทำให้ Claude เชื่อมต่อกับระบบภายนอกได้

พูดง่ายๆ คือ "ปลั๊กอิน" ที่ขยายความสามารถของ Claude ให้ทำงานกับ app และบริการต่างๆ ได้

```
ไม่มี MCP:
Claude รู้แค่สิ่งที่คุณพิมพ์ใน chat

มี MCP:
Claude เข้าถึง Gmail → อ่านอีเมลได้จริง
Claude เข้าถึง Calendar → ดูและเพิ่มนัดได้
Claude เข้าถึง LINE OA → ส่งข้อความได้
```

### MCP ติดตั้งอย่างไร?

```
ขั้นที่ 1: ดาวน์โหลด Claude Desktop จาก claude.ai/download
ขั้นที่ 2: เลือก MCP ที่ต้องการใน Claude Desktop
ขั้นที่ 3: Connect และ Authorize ด้วยบัญชีที่ต้องการ
ขั้นที่ 4: ใช้งานใน chat ได้เลย
```

### ข้อควรรู้เรื่อง MCP

```
⚠️ MCP ต้องติดตั้งบนเครื่องที่ใช้งาน
   ไม่ติดตาม account เหมือน Skill

⚠️ ต้องเปิด Claude Desktop ไว้
   ถ้าปิดแอป MCP ก็ใช้ไม่ได้

⚠️ ให้สิทธิ์เท่าที่จำเป็น
   ไม่ควรให้สิทธิ์เกินความจำเป็น
```

### Use Case: ผู้ช่วยส่วนตัวจัดการ Email + Calendar

```
สถานการณ์: ผู้บริหารมี email เยอะ และนัดหมายซับซ้อน
อยากให้ AI ช่วยจัดการให้

ติดตั้ง:
- Gmail MCP
- Google Calendar MCP

สั่งงานได้เลย:
"สรุป email ที่ยังไม่ได้ตอบ 3 วันที่ผ่านมา
จัดกลุ่มตามความเร่งด่วน"

"เพิ่มนัดประชุม Marketing Review
วันศุกร์หน้า 14.00-15.30 น. เชิญทีมทั้งหมด"

ผลลัพธ์: ผู้ช่วยส่วนตัว AI ที่เข้าถึง email
         และ calendar จริงๆ
```

## 19. RAG คืออะไรและใช้งานจริง

### ปัญหาที่ RAG แก้

```
มีเอกสารเยอะมาก เช่น summary หุ้น 200 บริษัท
อยากถามว่า "บริษัทไหนพูดถึง AI disruption บ้าง?"

ปัญหา:
ส่งเอกสารทั้ง 200 ไฟล์เข้า Claude ไม่ได้
→ token เกิน + แพงมาก + Claude อ่านไม่ครบ
```

### RAG แก้ปัญหานี้อย่างไร?

**RAG** ย่อมาจาก **Retrieval-Augmented Generation** คือการให้ Claude ตอบจากเอกสารจำนวนมากได้อย่างแม่นยำ

```
แทนที่จะส่งทุกอย่าง → ดึงเฉพาะส่วนที่เกี่ยวข้องมาใส่ context

เหมือนห้องสมุดที่มีบรรณารักษ์:
คุณถาม → บรรณารักษ์หยิบหนังสือที่เกี่ยวข้องมา 3-5 เล่ม
Claude อ่านแค่ 3-5 เล่มนั้น → ตอบได้แม่นยำ
ไม่ต้องอ่านหนังสือทุกเล่มในห้องสมุด
```

### RAG ทำงานอย่างไร?

**ขั้นที่ 1 — เตรียมข้อมูล (ทำครั้งเดียว)**
```
เอกสารทั้งหมด → แบ่งเป็นชิ้นเล็กๆ (chunk)
→ แปลงเป็น Vector (ตัวเลขแทนความหมาย)
```

```
"กำไรสุทธิ"      → [0.7, 0.1, 0.9, 0.2, ...]

ความหมายใกล้กัน → ตัวเลขใกล้กัน
เหมือนแผนที่ความหมาย
```

## 21. Function Calling ใน API

### Function Calling คืออะไร?

**Function Calling** หรือเรียกอีกชื่อว่า **Tool Use** คือความสามารถที่ให้ Claude "เรียกใช้ฟังก์ชัน" ที่เราเขียนไว้ได้เอง โดย Claude ตัดสินใจเองว่าควรเรียกเมื่อไหร่และด้วยข้อมูลอะไร

ก่อนอธิบายต่อ ขอปูพื้น 2 คำก่อน:

```
Function (ฟังก์ชัน) = ชุดคำสั่งในโค้ดที่ทำงานอย่างใดอย่างหนึ่ง
เหมือน "สูตร" ที่รับข้อมูลเข้า แล้วทำงาน แล้วส่งผลออกมา

ตัวอย่าง:
get_stock_price("PTT") → รับชื่อหุ้น → ค้นหาราคา → ส่งราคากลับมา
send_email("สวัสดี")   → รับข้อความ → ส่งอีเมล → แจ้งว่าส่งแล้ว
```

### ต่างจากโค้ดปกติอย่างไร?

```
โค้ดปกติ (if/else):
โค้ดตัดสินใจเองว่าจะทำอะไร → Claude แค่ตอบข้อความ

Function Calling:
Claude ตัดสินใจเองว่าต้องเรียก function ไหน
โค้ดแค่รัน function ที่ Claude เลือก
```

### Flow การทำงาน 5 ขั้น

```
ขั้นที่ 1: คุณบอก Claude ว่ามี function อะไรให้ใช้บ้าง
           เช่น get_stock_price, send_email, search_web

ขั้นที่ 2: ผู้ใช้ถาม "ราคา PTT วันนี้เท่าไหร่?"

ขั้นที่ 3: Claude ตัดสินใจว่าต้องเรียก get_stock_price("PTT")
           → Claude ไม่ได้รัน function เอง แค่บอกว่าอยากเรียก

ขั้นที่ 4: โค้ดเราเป็นคนรัน function จริงๆ
           แล้วส่งผลลัพธ์กลับไปให้ Claude

ขั้นที่ 5: Claude ตอบผู้ใช้ด้วยข้อมูลจริง
```

> ⚠️ จุดสำคัญที่มือใหม่มักเข้าใจผิด:
> Claude ไม่ได้รัน function เอง — Claude แค่บอกว่า "ขอเรียก function นี้ด้วย input นี้"
> โค้ดเราต้องรัน function แล้วส่งผลกลับไปให้ Claude เอง

### เมื่อไหรควรใช้ Function Calling

```
✅ อยากให้ Claude ดึงข้อมูล real-time เช่น ราคาหุ้น, อากาศ
✅ อยากให้ Claude ส่งอีเมล, บันทึกข้อมูล, เรียก API ภายนอก
✅ อยากสร้าง chatbot ที่ตอบได้หลายแบบ โดยไม่ต้องเขียน if/else ทุก case

❌ งานที่ Claude ตอบได้จากความรู้เดิม → ไม่จำเป็นต้องใช้
❌ งาน chat ปกติทั่วไป → ใช้ Claude.ai ธรรมดาพอ
```

> 💡 ถ้าอยากได้โค้ดตัวอย่างเพื่อ implement จริง
> แค่บอก Claude ว่า "เขียน Python Function Calling สำหรับ [งานที่ต้องการ]" ได้เลยครับ

### Use Case: Chatbot ตอบคำถามหุ้นอัตโนมัติ

```
สถานการณ์: อยากสร้าง chatbot ตอบคำถามหุ้นได้หลากหลาย
โดยไม่ต้องเขียน if/else ทุก case

Functions ที่ให้ Claude ใช้:
- get_stock_price(ticker)       → ราคาปัจจุบัน
- get_financial_summary(ticker) → สรุปผลประกอบการ
- compare_stocks(t1, t2)        → เปรียบเทียบ 2 หุ้น

ผู้ใช้ถาม:
"PTT กับ PTTEP ตัวไหนน่าซื้อกว่า?"
→ Claude เรียก compare_stocks("PTT", "PTTEP") เอง
→ แสดงผลเปรียบเทียบทันที

ผลลัพธ์: Chatbot ที่ตอบได้หลากหลาย
         โดยไม่ต้องเขียน if/else ทุกกรณี
```

## 22. Agentic Loop

### Agentic Loop คืออะไร?

**Agentic Loop** (เอเจนติก ลูป) คือวงจรที่ Agent ทำงานซ้ำๆ โดยคิด → ทำ → ดูผล → คิดใหม่ → ทำใหม่ จนกว่าจะเสร็จ

ก่อนอธิบายต่อ ขอปูพื้นคำว่า Loop:

```
Loop = วนซ้ำ ทำสิ่งเดิมซ้ำๆ จนครบเงื่อนไข

เหมือนการซักผ้า:
ใส่ผ้า → เติมน้ำ → ซัก → บิด → ดูว่าสะอาดไหม
→ ถ้ายังไม่สะอาด → ซักใหม่ → วนซ้ำจนสะอาด → จบ
```

### ทำไม Agentic Loop ถึงสำคัญ?

```
Automation ธรรมดา (oppday_agent.py ของเรา):
อ่านไฟล์ → สรุป → บันทึก → จบ
Flow ตายตัว ไม่ยืดหยุ่น ไม่ปรับตัว

Agentic Loop:
รับเป้าหมาย → คิดว่าต้องทำอะไร
→ ทำ step แรก → ดูผล
→ ถ้าดี ทำ step ถัดไป
→ ถ้าไม่ดี ปรับแผนแล้วลองใหม่
→ วนซ้ำจนเป้าหมายสำเร็จ
```

### เปรียบให้เห็นภาพ

```
Automation = สายพานการผลิต
ทุก step ถูกกำหนดไว้ล่วงหน้า ทำตามลำดับ ไม่เบี่ยงแผน

Agentic Loop = นักสืบ
รับคดี → สืบหาเบาะแส → ได้ข้อมูลใหม่ → ปรับทิศทาง
→ สืบต่อ → จนคลี่คลายคดี
```

### องค์ประกอบของ Agentic Loop

```
1. Perceive  → รับรู้ input และผลลัพธ์จาก step ก่อน
2. Think     → Claude วิเคราะห์ว่าต้องทำอะไรต่อ
3. Act       → เรียก Tool, รันโค้ด, เขียนไฟล์
4. Observe   → ดูผลลัพธ์ว่าตรงเป้าหมายไหม
5. วนซ้ำ    → จนเสร็จหรือถึง limit ที่กำหนด
```

### เมื่อไหรควรใช้ Agentic Loop

```
✅ งานที่ไม่รู้ล่วงหน้าว่าต้องทำกี่ step
✅ งานที่ต้องปรับแผนตามผลลัพธ์ที่ได้
✅ งานที่ต้องการ "คิด" ไม่ใช่แค่ "ทำ"

❌ งาน routine ที่ flow ตายตัว → automation ธรรมดาพอ
❌ งานง่ายๆ step ชัดเจน → Agent เดียวพอ
```

### Use Case: Research Agent วิเคราะห์หุ้น

```
สถานการณ์: อยากให้ Agent วิเคราะห์หุ้นอย่างรอบด้าน
โดยไม่ต้องกำหนด step ทุกอย่างล่วงหน้า

รับ: "วิเคราะห์หุ้น ADVANC อย่างรอบด้าน"

Loop ที่เกิดขึ้น:
รอบ 1: ค้นหาข้อมูลพื้นฐาน ADVANC
รอบ 2: ดึงผลประกอบการ 4 ไตรมาสล่าสุด
รอบ 3: ค้นหาข่าวล่าสุดและ sentiment
รอบ 4: วิเคราะห์คู่แข่ง TRUE, DTAC
รอบ 5: ประเมิน valuation
รอบ 6: สรุปและให้ recommendation
รอบ 7: ตรวจสอบว่าครบถ้วนดีไหม → ครบ → จบ Loop

ผลลัพธ์: รายงานวิเคราะห์ครบด้าน
         โดยไม่ต้องกำหนดทุก step ล่วงหน้า
```

## 23. Tips ประหยัดเงินและ Optimize การใช้ API

### ทำไมต้องคิดเรื่องนี้?

API คิดเงินตาม token — ถ้าไม่ระวัง ค่าใช้จ่ายอาจสูงเกินความจำเป็น

```
ตัวอย่างความต่างชัดๆ:
งานสรุป Oppday 200 ไฟล์:

Opus   → ~$54  (แพงมาก)
Sonnet → ~$10  (สมเหตุสมผล)
Haiku  → ~$2   (ถูกมาก)

เลือก Model ให้ถูกงาน = ประหยัดได้ 80-90%
```

### Tip 1: เลือก Model ให้เหมาะกับงาน

```
Claude Haiku — ถูกที่สุด เร็วที่สุด
เหมาะกับ:
→ จัดหมวดหมู่ข้อความ (classification)
→ ดึงข้อมูลจาก template ที่กำหนดไว้แล้ว
→ แปลภาษา
→ สรุปสั้นๆ ที่ไม่ต้องการความลึก

Claude Sonnet — สมดุลราคาและคุณภาพ (แนะนำสำหรับงานส่วนใหญ่)
เหมาะกับ:
→ สรุปเอกสารยาว เช่น Earnings Call
→ วิเคราะห์ทั่วไป
→ เขียนโค้ด
→ งานที่ต้องการคุณภาพดีในราคาสมเหตุสมผล

Claude Opus — แพงที่สุด ฉลาดที่สุด
เหมาะกับ:
→ งาน reasoning ซับซ้อนมาก
→ งานที่ต้องการความแม่นยำสูงสุด
→ งานเฉพาะทางที่ Sonnet ทำได้ไม่ดีพอ
```

### Tip 2: เขียน Prompt ให้สั้นแต่ได้ผล

```
❌ Prompt ฟุ่มเฟือย (เสีย token มาก):
"สวัสดีครับ Claude ผมอยากให้คุณช่วยผมสรุปเอกสารนี้
ถ้าคุณมีเวลา ช่วยสรุปให้สั้นๆ ประมาณ 5 บรรทัด
ขอบคุณมากนะครับ"

✅ Prompt กระชับ (ประหยัด token 60%):
"สรุปเอกสารนี้เป็น 5 bullet points ภาษาไทย"
```

### Tip 3: ใช้ Caching สำหรับ System Prompt ยาวๆ

```
System Prompt ยาว + ส่งซ้ำทุก API call = เสียเงินมาก

วิธีแก้: ใช้ Prompt Caching
→ จ่ายครั้งแรกครั้งเดียว
→ ครั้งถัดไปถูกกว่า 90%
→ เหมาะกับ Agent ที่รัน batch หลายครั้ง
```

### Tip 4: Batch Processing แทน Real-time

```
Real-time:
ส่ง API call ทีละ 1 → รอผล → ส่งต่อไป

Batch Processing (ถูกกว่า ~50%):
รวม request ทั้งหมด → ส่งพร้อมกัน → ได้ผลทีหลัง

เหมาะกับ: งานที่ไม่ต้องการผลทันที
เช่น batch summarize Oppday ทุกคืน
```

### Tip 5: ตรวจสอบการใช้งานใน Console

```
ไปที่ console.anthropic.com → Usage
→ ดูว่าเสีย token ไปกับอะไรมากที่สุด

สิ่งที่มักเสีย token โดยไม่รู้ตัว:
- System Prompt ที่ยาวเกินจำเป็น
- ส่ง context เก่าซ้ำๆ ใน conversation
- ส่งไฟล์ทั้งหมดแทนที่จะใช้ RAG
```

### Tip 6: รับมือ Rate Limits เมื่อรัน Agent Batch

**Rate Limit** คือข้อจำกัดจำนวน API call ที่ทำได้ในช่วงเวลาหนึ่ง

```
RPM = Requests Per Minute (จำนวน request ต่อนาที)
TPM = Tokens Per Minute (จำนวน token ต่อนาที)

ถ้าส่งเร็วเกินไป → Error 429: Too Many Requests
→ Agent หยุดทำงานกลางคัน
```

**แนวทางรับมือ:**
```
✅ ใส่ delay รอ 1-2 วินาทีระหว่างทุก API call
✅ เขียน retry logic — ถ้าเจอ Error 429 ให้รอแล้วลองใหม่
✅ รัน batch ช่วง off-peak เช่น กลางคืน
✅ ดู rate limit ของ tier ที่ใช้ที่ console.anthropic.com
```

> 💡 ถ้าอยากได้โค้ด retry logic พร้อมใช้
> แค่บอก Claude ว่า "เขียน Python retry handler สำหรับ Anthropic API Error 429" ได้เลยครับ

### Use Case: Optimize oppday_agent ให้ประหยัดขึ้น

```

การปรับที่ทำได้:

   ประหยัด: ~80%
```
